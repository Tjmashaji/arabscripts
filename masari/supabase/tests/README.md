# اختبارات قاعدة البيانات

سيناريوهات كاملة تُشغَّل في Supabase ← SQL Editor. كل سيناريو ينشئ حسابات وهمية وبيانات داخل
عملية واحدة، ثم يُنهيها بخطأ مقصود يعرض النتائج (`RESULT ...`)، فتُلغى كل التغييرات ولا يبقى شيء في البيانات.

- `school_day.sql`: يوم دراسي كامل لكل الأدوار (33 فحصًا): التعيين، التفعيل، الطلاب والسائقين، المسار، الرحلة،
  اعتماد المحطات بالموقع، الحضور، البلاغات، الإشعارات، العزل بين المستخدمين والمناطق.

- `isolation.sql`: مدرستان في نفس المنطقة (29 فحصًا): المدرسة لا ترى ولا تعدّل بيانات مدرسة أخرى، ولي الأمر لا يرى
  إلا ابنه ولا يسجل غياب غيره، السائق لا يرسل موقعًا ولا يبدأ أو ينهي رحلة ليست له، لا أحد يمنح نفسه صلاحيات،
  الزائر بلا دخول لا يرى شيئًا، لا يتكرر الصعود، ولا تنتهي رحلة العودة وطالب ما زال في الباص.

- `school_ops.sql`: عمليات المدرسة (16 فحصًا): استيراد الطلاب من ملف مع سبب كل صف خاطئ، اعتماد الطلبات دفعة واحدة،
  إنشاء رحلات اليوم يدويًا وتلقائيًا كل صباح (بلا تكرار، والملغاة لا تُعاد، ولا رحلات في الإجازة)، وملخص للمدرسة بما تعذّر.

كل سطر في النتيجة يبدأ بـ PASS أو FAIL. أي FAIL يعني أن تغييرًا في قاعدة البيانات كسر سلوكًا متوقعًا.

## التشغيل المحلي والتلقائي

`npm run test:db` يشغّل كل الملفات أعلاه على Postgres 16 مؤقت بدون Supabase ولا Docker: ينشئ قاعدة فارغة، يضع فيها
بديلًا مصغرًا لما توفّره Supabase (`local/supabase_stub.sql`: auth.uid والأدوار والتخزين وpg_cron وpg_net)، يطبّق كل
الترحيلات بالترتيب، ثم يطبع PASS/FAIL لكل فحص ويفشل إن وُجد FAIL. يعمل تلقائيًا في GitHub Actions مع كل تعديل على مساري.
