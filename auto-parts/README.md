# منصة وساطة قطع غيار السيارات الصينية

تطبيق Next.js + Supabase وفق وثيقة المواصفات التنفيذية (الإصدار 1.0). العربية افتراضية (RTL)، مع الإنجليزية والصينية المبسطة.

## حالة المراحل

| المرحلة | الحالة |
|---|---|
| A — التأسيس: قاعدة البيانات، الدخول، الأدوار، الفصل بين المنشآت، RTL، تعدد اللغات | **مكتملة** (انظر «ما ينقص» أدناه) |
| B1 — الشركاء: الدعوات، طلب الاعتماد، المستندات الخاصة، مراجعة الإدارة | **مكتملة** (الدعوة تُرسل كرابط يُنسخ؛ الإرسال بالبريد يحتاج ربط خدمة بريد) |
| B2 — الكتالوج: المنتجات والعروض والتوافق والبحث | **مكتملة** |
| C — طلبات التسعير، عروض الموردين، التسعيرة المفصّلة، الموافقة وإنشاء الطلب | **مكتملة** (الدفع غير مفعّل: الطلب يبقى «بانتظار الدفع») |
| D — الشحن اليدوي، الشحنات والتتبع، لوحة الناقل، إدارة الطلبات، التقارير والإعدادات | **مكتملة** (لا تكامل شحن آلي ولا دفع إلكتروني) |
| E — الأمان والاختبار والنسخ الاحتياطي والإطلاق التجريبي | **مكتملة تقنيًا**؛ قبل الإطلاق التجاري: البنود المفتوحة في «قائمة الإطلاق» أدناه |
| F — مساعد التأكيد الآلي: مكالمة بالعربي عند صدور التسعيرة وعند إنشاء الطلب، وواتساب إن لم يرد العميل | **مكتملة تقنيًا**؛ تعمل بعد فتح حسابي Vapi وTwilio وضبط الإعدادات (انظر «مساعد التأكيد الآلي») |

## التشغيل محليًا

```bash
cp .env.example .env.local   # القيم العامة لمشروع Supabase المستقل «auto-parts» موجودة فيه
npm install
npm run dev                  # http://localhost:3000
```

| الأمر | ماذا يفعل |
|---|---|
| `npm run lint` / `npm run typecheck` | فحص الكود والأنواع |
| `npm test` | اختبارات الوحدة (ملفات الترجمة متطابقة، اتجاه اللغات، منع التحويل لمواقع خارجية) |
| `npm run test:backup` | يختبر سكربتي النسخ والاستعادة محليًا: نسخة سليمة تُستعاد بنجاح، ونسخة ناقصة واختلاف هيكل يُكتشفان |
| `npm run test:db` | يطبّق الترحيلات على Postgres 16 مؤقت ويشغّل `supabase/tests/*.sql` (العزل والصلاحيات). يحتاج initdb وpsql |
| `npm run build && npm run test:e2e` | اختبارات متصفح على الجوال وسطح المكتب. تقرأ من Supabase الحقيقي ومحاولة دخول خاطئة فقط، ولا تنشئ بيانات |

## متغيرات البيئة

| المتغير | إلزامي | الوصف |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | نعم | عنوان مشروع Supabase |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | نعم | المفتاح العام (`sb_publishable_…`). آمن للمتصفح؛ الحماية عبر RLS |
| `NEXT_PUBLIC_SITE_URL` | نعم في الإنتاج | عنوان الموقع، تُبنى منه روابط تفعيل البريد |
| `NEXT_PUBLIC_PLATFORM_NAME` | لا | اسم المنصة الظاهر. فارغ = الوصف العام من ملفات الترجمة. المساعد الآلي يعرّف نفسه به |
| `CONTACT_WORKER_TOKEN` | للمساعد الآلي | رمز عشوائي (32 حرفًا فأكثر). نفس القيمة في `ap_private.contact_settings.worker_token` |
| `VAPI_API_KEY` / `VAPI_PHONE_NUMBER_ID` / `VAPI_WEBHOOK_SECRET` | للمكالمات | مفتاح Vapi الخاص، معرّف رقم المتصل في Vapi، وسر عشوائي يتحقق به `/api/contact/webhook` |
| `CONTACT_MODEL` / `CONTACT_VOICE` | لا | نموذج Claude للمكالمة (افتراضي `claude-haiku-5-5`، الأسرع في الرد) وصوت Azure (افتراضي `ar-SA-HamedNeural`) |
| `TWILIO_ACCOUNT_SID` / `TWILIO_AUTH_TOKEN` / `TWILIO_WHATSAPP_FROM` | لواتساب | حساب Twilio ورقم واتساب المرسل بصيغة `+966…` |
| `TWILIO_TEMPLATE_QUOTE_READY` / `TWILIO_TEMPLATE_ORDER_CONFIRM` | لواتساب | معرّفا القالبين المعتمدين (`HX…`) |

لا يستخدم التطبيق مفتاح `service_role`. كل الكتابة الحساسة تمر بدوال قاعدة بيانات تتحقق من الصلاحية. المفاتيح السرية الوحيدة لخدمات المساعد الآلي الخارجية، وتبقى على الخادم (`src/lib/contact-server.ts`).

## النشر (Vercel)

1. Import المستودع واختيار المجلد الجذر `auto-parts`.
2. إضافة متغيرات البيئة أعلاه، و`NEXT_PUBLIC_SITE_URL` = النطاق الفعلي.
3. في Supabase ← Authentication ← URL Configuration: إضافة `https://<النطاق>/auth/confirm` إلى Redirect URLs.
4. إعداد SMTP خاص (Authentication ← SMTP). البريد الافتراضي في Supabase محدود جدًا ولا يصلح لمستخدمين حقيقيين.
5. **المنطقة:** دوال Vercel يجب أن تعمل في نفس منطقة قاعدة البيانات، وإلا تتكرر رحلة بين القارات مع كل استعلام. `vercel.json` يحددها `fra1` لأن مشروع Supabase (`auto-parts-eu`) في فرانكفورت (eu-central-1)، وهي الأقرب للسعودية بين المناطق المتاحة. عند نقل قاعدة البيانات لمنطقة أخرى غيّرها لنفس المنطقة.

## قاعدة البيانات

- الترحيلات في `supabase/migrations`. تُطبّق على مشروع جديد دفعة واحدة عبر `supabase/manual/setup_new_project.sql` (SQL Editor ← Run).
- كانت المنصة على مشروع مشترك، لذلك كل الجداول والأنواع تبدأ بـ `ap_`، والدوال المساعدة في مخطط `ap_private` غير المنشور عبر API.
- لا يوجد مشغّل على `auth.users`؛ الملف الشخصي يُنشأ عند أول دخول عبر `ap_ensure_profile`.

| الجدول | الغرض |
|---|---|
| `ap_locales` | اللغات المفعّلة واتجاه الكتابة |
| `ap_profiles` | ملف المستخدم (الاسم، الجوال، الحالة) |
| `ap_user_preferences` | اللغة المفضلة والمنطقة الزمنية |
| `ap_roles_permissions` | مصفوفة صلاحيات أدوار الإدارة |
| `ap_staff_roles` | أدوار فريق الإدارة لكل مستخدم |
| `ap_organizations` | المنشآت (pending / active / suspended) |
| `ap_organization_members` | أعضاء المنشأة (owner / admin / staff) |
| `ap_organization_verifications` | كل صفة (وسيط، بائع، مورد، مصنع، ناقل) تُعتمد أو تُرفض منفصلة، مع السبب ومتخذ القرار |
| `ap_audit_logs` | سجل تدقيق تلقائي بمشغّلات، للقراءة فقط |
| `ap_platform_settings` | إعدادات المنصة (مثل أقصى عمر لتأكيد التوفر: 48 ساعة) |

### تعيين أول مدير أعلى (مرة واحدة)

1. أنشئ حسابك من `/signup` وفعّل البريد وسجّل الدخول مرة.
2. في Supabase ← SQL Editor:

```sql
insert into public.ap_staff_roles (user_id, role)
select id, 'super_admin' from auth.users where email = 'بريدك@example.com';
```

بعدها تُدار بقية الأدوار من `/admin/access`.

## مسار الشريك (B1)

1. المدير ينشئ دعوة من `/admin/invitations` (بريد + صفات + لغة + مدة). الرمز عشوائي (32 بايت)، يُخزَّن بصمته فقط، ويُعرض الرابط مرة واحدة.
2. المدعو يفتح `/invite/<token>`، يسجّل أو يدخل **بنفس البريد المدعو**، ثم يقبل الدعوة: تُنشأ منشأة معلّقة وطلب اعتماد مسودة.
3. يعبّئ `/partner/application`: بيانات المنشأة والممثل والصفات والإقرار، ويرفع المستندات (PDF/JPG/PNG حتى 4MB، يُفحص النوع من محتوى الملف) إلى مساحة تخزين خاصة `ap-verification-docs`.
4. يرسل الطلب؛ لا يُقبل الإرسال قبل اكتمال الحقول الإلزامية ووجود مستند واحد على الأقل.
5. المدير يراجع من `/admin/partner-applications`: موافقة على صفات محددة، رفض، أو طلب تعديل (السبب إلزامي). الموافقة على طلب ناقص تحتاج سبب استثناء يُسجَّل.
6. فتح أي مستند يمر بـ `/api/documents/<id>`: يُسجَّل في سجل التدقيق ثم رابط مؤقت لدقيقة.

جدول الصفات المطلوبة لكل طلب (`partner_application_roles` في الوثيقة) هو `ap_organization_verifications`.

## الكتالوج (B2)

- **تعريف القطعة منفصل عن العروض:** `ap_products` (الاسم، العلامة، الفئة، الوصف بلغته الأصلية) و`ap_product_offers` (عرض لكل منشأة: نوع القطعة، السعر بعملته، بلد التوريد، مدة التوريد، الصلاحية).
- **أرقام القطع** في `ap_product_identifiers` تُحفظ كما كُتبت، ويُبحث فيها بصيغة موحّدة (بلا مسافات أو شرطات، أحرف كبيرة).
- **التوفر:** كل تأكيد يُحفظ في `ap_inventory_snapshots`. العرض «متوفر» للزائر فقط إن أُكّد خلال `availability_max_age_hours` (48 افتراضيًا). المخزون المجهول `null` لا صفر. تغيير السعر يُسقط التأكيد السابق.
- **النشر:** المنتج مسودة ← بانتظار المراجعة ← منشور/مرفوض (بسبب) ← موقوف. لا يضيف منتجًا أو عرضًا إلا شريك معتمد بصفة بائع أو مورد أو مصنع، ومنشأته نشطة.
- **العرض العام:** `ap_search_products` و`ap_public_offers` لا تكشفان هوية المنشأة (بلد التوريد فقط)، ولا تعرضان إلا المنشور والنشط وغير المنتهي من منشآت ما زالت معتمدة.
- الموديلات يضيفها المدير من `/admin/catalog`؛ العلامات الخمس والفئات العامة مُضافة مسبقًا.

## طلبات التسعير والطلبات (C)

1. العميل (بعد الدخول) يرسل `/request-part`: العلامة والموديل والسنة والمحرك، رقم الهيكل (اختياري، 17 خانة)، رقم القطعة، الوصف، الكمية، المدينة، الجوال، وحتى 3 صور في مستودع خاص `ap-request-media`. موافقة الخصوصية إلزامية، وحد 10 طلبات في الساعة. من صفحة المنتج زر «اطلب تأكيد السعر والتوفر» يفتح الطلب مربوطًا بالمنتج والعرض.
2. الإدارة (`quotes.manage`) من `/admin/quotes/<id>` ترسل الطلب لمنشآت معتمدة للبيع فقط، وتقرر مشاركة رقم الهيكل أو لا.
3. المورد يرى في `/partner/requests` الطلبات المرسلة له فقط عبر `ap_supplier_requests`: بلا اسم العميل وجواله، ورقم الهيكل فقط إن شوركه. فتح الصور يُسجَّل في التدقيق. عرض واحد لكل منشأة (يُحدَّث)، ولا يرى عروض المنافسين.
4. الإدارة تقارن العروض، وتنشئ مسودة تسعيرة (الإصدار التالي) ببنود: سعر القطعة، الشحن الدولي والمحلي، الجمارك، الضريبة، رسوم الخدمة، خصم، أخرى. لكل بند حالة «مؤكد/تقديري» ومصدر ومستفيد. المبالغ بالريال؛ الخصم وحده سالب.
5. الإصدار يتطلب صلاحية مستقبلية وشروط إلغاء والبائع المسؤول وبند قطعة. قاعدة البيانات تحسب الإجمالي وتعلّم وجود بنود تقديرية، ويصبح الإصدار السابق «مستبدلًا». العميل لا يرى المسودات.
6. العميل يوافق على أحدث إصدار صالح فقط: تُحفظ نسخة ثابتة (`snapshot`) ويُنشأ طلب `ORD-…` بحالة `awaiting_payment` وحالة دفع `unpaid` لا يغيّرها العميل. لا تحصيل أموال في هذه المرحلة.

## الشحن والتشغيل (D)

- **الناقل** (منشأة معتمدة بصفة `carrier`) يدير من `/carrier` خدماته ومناطق تغطيته، ويسعّر طلبات عروض الشحن، ويحدّث الشحنات المسندة إليه ويرفع إثبات التسليم والفواتير إلى مستودع خاص `ap-shipment-docs`. لا يرى بيانات العميل أو المورد أو أسعار القطع؛ يرى بيانات التسليم فقط في الشحنة المسندة.
- **عروض الشحن** (`ap_shipping_quotes`) تُطلب من ناقل معتمد ببيانات الطرد (الوزن الفعلي والحجمي والأبعاد والمسار)، أو تُدخلها الإدارة يدويًا من ناقل خارجي. الجدول جاهز للربط الآلي لاحقًا (`pricing_source`، `provider_quote_reference`)، ولا يوجد أي تكامل آلي الآن.
- **اعتماد عرض الشحن في التسعيرة** يستبدل بند الشحن الدولي بدل إضافته. التسعيرة لا تصدر إن احتوت أكثر من بند لنفس نوع الشحن. العرض بعملة مختلفة يحتاج مبلغًا محوّلًا ومصدر سعر صرف مكتوبًا.
- **الدفع:** لا تحصيل عبر المنصة. المالية (`finance.manage`) تسجّل من `/admin/orders/<id>` دفعة استلمها البائع المسؤول خارج المنصة؛ المبلغ يطابق الإجمالي، ولا تُسجَّل مرتين، وتُحفظ في `ap_payments` وفي سجل التدقيق.
- **حالة الطلب** تتغير فقط وفق `ap_order_transitions` (مدير/مورد/عميل/نظام). المورد يبدأ التجهيز ثم «جاهز للشحن» بعد الدفع من `/partner/orders`. لا تُنشأ شحنة قبل الدفع والجاهزية. مراحل الشحنة تتقدم فقط، ورقم التتبع إلزامي من الاستلام، وحالة الطلب تتبعها تلقائيًا. العميل يؤكد الاستلام فيكتمل الطلب.
- **التقارير** `/admin/reports` (`reports.read`): الطلبات والتسعير والتحويل والشحنات المتأخرة، وتفصل إجمالي قيمة الطلبات عن رسوم الخدمة وصافيها بعد الخصومات لكل عملة. تصدير CSV بلا بيانات شخصية.
- **الإعدادات** `/admin/settings` (`settings.edit`): نسبة رسوم الخدمة المقترحة وصلاحية تأكيد التوفر.

## مساعد التأكيد الآلي (F)

مكالمة صوتية بالعربي يجريها مساعد آلي (Vapi، والعقل Claude) في حالتين، **فقط إن وافق العميل** بخانة اختيارية في `/request-part`:

| متى | ماذا يقول | النتائج |
|---|---|---|
| صدور التسعيرة | التسعيرة جاهزة في حسابك، الإجمالي ومدة التوصيل، هل تنوي الموافقة؟ (الموافقة نفسها من الموقع) | أكّد / رفض / يطلب موظفًا / غير واضح |
| إنشاء الطلب | يؤكد القطعة والكمية والمدينة والإجمالي، وأن الطلب ما زال مطلوبًا. لا دفع في المكالمة | نفسها |

- **لم يرد** (أو مشغول أو بريد صوتي): رسالة واتساب بقالب معتمد. **تعذّر الاتصال**: إعادة بعد 30 دقيقة، مرتين كحد أقصى.
- **لا شيء يتغير تلقائيًا:** النتيجة وملخص المكالمة يظهران للإدارة في صفحة الطلب `/admin/orders/<id>` وصفحة التسعيرة `/admin/quotes/<id>`، مع زر «اتصل مرة ثانية».
- **ساعات الاتصال:** 9 صباحًا إلى 9 مساءً بتوقيت الرياض. خارجها تنتظر المهمة، وتلتقطها جولة كل 10 دقائق.
- **الإفصاح:** أول جملة في المكالمة أنه مساعد آلي. لا يذكر الجوال ولا رقم الهيكل، ولا يقبل بيانات دفع، ولا يعد بأسعار أو مواعيد غير ما في التسعيرة.

**كيف يعمل:** صدور التسعيرة أو إنشاء الطلب ينشئ صفًا في `ap_contact_jobs` وتنبّه قاعدة البيانات `/api/contact/dispatch` عبر pg_net، فيستلم الخادم المهام بدالة `ap_contact_claim` ويبدأ المكالمة عبر Vapi. أثناء المكالمة يستدعي Claude أداة `record_outcome`، وفي نهايتها يرسل Vapi تقريرًا إلى `/api/contact/webhook`. الدالتان المتاحتان للخادم بلا جلسة محميتان برمز العامل، ولا يوجد مفتاح `service_role`.

### التفعيل (مرة واحدة)

1. **قاعدة البيانات:** شغّل `supabase/manual/phase_g_contact.sql` في SQL Editor (أو الترحيل `20261026090000_ap_contact.sql`). يفعّل pg_net وpg_cron ويجدول الجولة.
2. **Twilio:** رقم يقبل الاتصال بالجوالات السعودية، ومرسل واتساب معتمد، وقالبان من نوع Utility بالعربي، مثلًا:
   - التسعيرة: `هلا {{1}}، تسعيرة طلبك ({{2}}) جاهزة في حسابك. رقم الطلب {{3}}. حاولنا نتصل عليك ولا وصلنا لك.`
   - الطلب: `هلا {{1}}، استلمنا طلبك ({{2}}) رقم {{3}}. حاولنا نتصل نأكده معك؛ رد على هالرسالة لو فيه أي تعديل.`
3. **Vapi:** أنشئ حسابًا، واستورد رقم Twilio (Phone Numbers ← Import)، وانسخ معرّف الرقم والمفتاح الخاص.
4. **Vercel:** أضف المتغيرات أعلاه. `VAPI_WEBHOOK_SECRET` و`CONTACT_WORKER_TOKEN` قيم عشوائية طويلة (مثلًا `openssl rand -hex 32`).
5. **التشغيل:** في SQL Editor:
   ```sql
   update ap_private.contact_settings set enabled = true,
     dispatch_url = 'https://<النطاق>/api/contact/dispatch', worker_token = '<نفس CONTACT_WORKER_TOKEN>';
   ```
   الإيقاف الفوري: `update ap_private.contact_settings set enabled = false;` (المكالمات الجارية تكتمل).
6. **التجربة:** أرسل طلبًا من حسابك مع خانة الموافقة وجوالك، ثم أصدر له تسعيرة. يصل الاتصال خلال ثوانٍ (داخل ساعات الاتصال)، وتظهر النتيجة في صفحة التسعيرة.

**النظام:** الاتصال الآلي التسويقي محظور بلا موافقة، وهذه المكالمات خدمية تخص طلب العميل وبموافقته الصريحة. مع ذلك راجع اشتراطات هيئة الاتصالات والفضاء والتقنية ونظام حماية البيانات الشخصية قبل الإطلاق العام، خصوصًا تسجيل المكالمات (Vapi يحفظ التسجيل والنص افتراضيًا).

- العميل يرى ويعدّل ملفه فقط (الاسم والجوال)، ولا يعدّل حالته.

## صفحات الثقة والظهور في البحث

- **صفحات:** من نحن، كيف نعمل، الأسئلة الشائعة، سياسة الخصوصية، الشروط والأحكام (بالعربية والإنجليزية والصينية، المحتوى في `messages/*.json` ← `pages`). نصوص السياسات تصف ما يفعله النظام فعلًا، **ويجب أن يراجعها مستشار قانوني قبل الإطلاق التجاري**.
- **بيانات الجهة المشغّلة** (الاسم النظامي، السجل التجاري، بريد وواتساب التواصل) تُدخل من `/admin/settings` وتظهر في التذييل وصفحة «من نحن» فقط بعد إدخالها.
- **تتبع الطلب بلا حساب** `/track`: رقم الطلب + جوال الطلب كاملًا؛ يعرض الحالة ومراحل الشحن فقط، ويُقفل رقم الطلب بعد 10 محاولات خاطئة في الساعة.
- **محركات البحث:** `sitemap.xml` بكل اللغات مع hreflang (الصفحات العامة، صفحة لكل علامة `/brands/<slug>`، المنتجات المنشورة)، `robots.txt` يستبعد الحسابات واللوحات، روابط canonical وhreflang في الصفحات العامة، بيانات منظمة (WebSite + SearchAction) في الرئيسية، وOpen Graph.
- **صفحة خطأ** واضحة مع رقم مرجعي، وصفحة احتياطية إذا تعطل التخطيط.

## الأمان (E)

- **فحوص الكتالوج** (`supabase/tests/security.sql`) تشمل كل جدول ودالة حاليًا ومستقبلًا: RLS مفعّل على كل جداول المنصة؛ لا إدراج أو حذف من المتصفح؛ التعديل المباشر محصور في أعمدة معروفة (الاسم والجوال والتفضيلات وحقول المنشأة القابلة للتعديل وقراءة الإشعارات)؛ كل دالة `SECURITY DEFINER` لها `search_path` ثابت؛ الزائر لا ينفّذ إلا البحث والعروض العامة وفحص الدعوة وتتبع الطلب ودالتي عامل الاتصال (محميتين برمز سري)؛ كل المستودعات خاصة عدا صور المنتجات؛ السجلات التاريخية للقراءة فقط.
- **على المشروع الحقيقي:** شغّل `supabase/manual/security_check.sql` في SQL Editor (قراءة فقط). النتيجة المطلوبة «No rows returned».
- **اختبارات العزل ورفع الصلاحيات (IDOR):** في `foundation.sql` و`partners.sql` و`catalog.sql` و`quotes.sql` و`shipping.sql` و`contact.sql` — كل دور يحاول الوصول لبيانات غيره أو تنفيذ ما ليس له. كل حماية مهمة اختُبرت بإضعافها عمدًا والتأكد أن الاختبار يفشل.
- **ترويسات HTTP:** سياسة أمان المحتوى (CSP: لا سكربتات أو إطارات أو اتصالات خارجية، الصور الخارجية من تخزين Supabase فقط)، HSTS، منع التضمين في إطارات، `nosniff`. اختبار متصفح يتأكد أنها موجودة وأن الصفحات تعمل بلا مخالفات.
- **حدود المعدل:** Supabase Auth يحد محاولات الدخول والتسجيل وإرسال البريد (Authentication ← Rate Limits). طلبات التسعير: 10 لكل عميل في الساعة. قبل الإطلاق العام يُنصح بتفعيل CAPTCHA (Authentication ← Attack Protection).
- **مراقبة التوفر:** `/api/health` يعيد 200 إن ردت قاعدة البيانات خلال 3 ثوانٍ و503 غير ذلك. اربطه بخدمة مراقبة مجانية (مثل UptimeRobot) كل 5 دقائق.

## النسخ الاحتياطي والاستعادة

خطة Supabase المجانية لا توفر نسخًا قابلة للتنزيل، لذلك يعمل `.github/workflows/auto-parts-backup.yml` يوميًا (03:15 بتوقيت الرياض، ويمكن تشغيله يدويًا من Actions):

1. `supabase/backup/backup.sh` ينسخ بيانات المنصة وحسابات الدخول وهيكل الإنتاج، مع عدد صفوف كل جدول من نفس اللقطة.
2. `supabase/backup/restore-check.sh` يستعيد النسخة فعليًا في قاعدة مؤقتة من الترحيلات ويتحقق: عدد الصفوف = الإنتاج، الهيكل = الترحيلات، فحوص الأمان تمر. فشل أي منها يُفشل التشغيل ويصلك بريد من GitHub.
3. النسخة تُشفَّر (AES-256) وتُحفظ 14 يومًا في Artifacts التشغيل.

**الإعداد (مرة واحدة)** — في GitHub ← Settings ← Secrets and variables ← Actions ← New repository secret:
- `SUPABASE_DB_URL`: من Supabase ← Connect ← **Session pooler** (ليس Direct)، مع وضع كلمة مرور قاعدة البيانات مكان `[YOUR-PASSWORD]`.
- `BACKUP_PASSPHRASE`: عبارة طويلة عشوائية. **احفظها خارج GitHub** (مدير كلمات مرور)؛ بدونها لا يمكن فك أي نسخة.

**الاستعادة في مشروع Supabase جديد (عند الكارثة):**
1. نزّل الملف من Actions ← آخر تشغيل ناجح ← Artifacts، ثم: `gpg -d auto-parts-*.tar.gz.gpg > backup.tar.gz && tar -xzf backup.tar.gz`
2. أنشئ مشروعًا جديدًا وشغّل `supabase/manual/setup_new_project.sql` (وأي ترحيل أحدث).
3. بالاتصال المباشر (`psql "<رابط Session pooler>"`): `set session_replication_role = replica;` ثم `\i auth-data.sql`، ثم أفرغ جداول `ap_` (`truncate` لكل جدول) و`\i app-data.sql`.
4. حدّث متغيرات Vercel وعناوين الدخول (Site URL وRedirect URLs) كما في «النشر».

**لا تشمل النسخة ملفات التخزين** (مستندات الاعتماد، صور الطلبات والمنتجات، مستندات الشحن)؛ قاعدة البيانات تحفظ بياناتها الوصفية فقط. خطة Pro توفر نسخًا يومية لقاعدة البيانات، أما الملفات فتحتاج نسخًا منفصلًا عبر واجهة S3 في Supabase (قرار مفتوح).

### الإطلاق التجريبي (سيناريو كامل بحسابات تجريبية)

1. **المدير:** ينشئ دعوة مورد ودعوة ناقل من `/admin/invitations`، ويضيف موديلًا من `/admin/catalog`.
2. **المورد والناقل:** يقبلان الدعوة، يكملان طلب الاعتماد ويرفعان مستندًا؛ **المدير** يعتمدهما.
3. **المورد:** يضيف منتجًا برقم قطعة وتوافق وصورة ويرسله؛ **المدير** ينشره؛ **المورد** يضيف عرضًا ويؤكد التوفر. تحقق أنه يظهر في `/products`.
4. **العميل:** يطلب تأكيد السعر من صفحة المنتج، وطلب قطعة غير موجودة من `/request-part`.
5. **المدير:** يرسل الطلب للمورد؛ **المورد** يقدّم عرضه؛ **المدير** يطلب عرض شحن من الناقل؛ **الناقل** يسعّره.
6. **المدير:** ينشئ التسعيرة من عرض المورد، يعتمد عرض الشحن، يضيف رسوم الخدمة، ويصدرها؛ **العميل** يوافق.
7. **المالية (أو المدير الأعلى):** تسجّل الدفع؛ **المورد:** «بدء التجهيز» ثم «جاهز للشحن»؛ **المدير:** ينشئ الشحنة.
8. **الناقل:** يقبل، يسجّل رقم التتبع، يحدّث المراحل، يرفع إثبات التسليم، «تم التسليم»؛ **العميل:** يؤكد الاستلام.
9. **التحقق:** التقرير في `/admin/reports` يطابق الأرقام، وسجل التدقيق يحوي كل خطوة، وكل طرف لم يرَ إلا ما يخصه.
