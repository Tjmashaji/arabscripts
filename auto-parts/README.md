# منصة وساطة قطع غيار السيارات الصينية

تطبيق Next.js + Supabase وفق وثيقة المواصفات التنفيذية (الإصدار 1.0). العربية افتراضية (RTL)، مع الإنجليزية والصينية المبسطة.

## حالة المراحل

| المرحلة | الحالة |
|---|---|
| A — التأسيس: قاعدة البيانات، الدخول، الأدوار، الفصل بين المنشآت، RTL، تعدد اللغات | **مكتملة** (انظر «ما ينقص» أدناه) |
| B1 — الشركاء: الدعوات، طلب الاعتماد، المستندات الخاصة، مراجعة الإدارة | **مكتملة** (الدعوة تُرسل كرابط يُنسخ؛ الإرسال بالبريد يحتاج ربط خدمة بريد) |
| B2 — الكتالوج: المنتجات والعروض والتوافق والبحث | **مكتملة** |
| C — طلبات التسعير، عروض الموردين، التسعيرة المفصّلة، الموافقة وإنشاء الطلب | **مكتملة** (الدفع غير مفعّل: الطلب يبقى «بانتظار الدفع») |
| D — الشحن ولوحات الإدارة والتقارير | لم تبدأ |
| E — الأمان والاختبار والإطلاق التجريبي | لم تبدأ |

## التشغيل محليًا

```bash
cp .env.example .env.local   # القيم العامة لمشروع Supabase المستقل «auto-parts» موجودة فيه
npm install
npm run dev                  # http://localhost:3000
```

| الأمر | ماذا يفعل |
|---|---|
| `npm run lint` / `npm run typecheck` | فحص الكود والأنواع |
| `npm test` | اختبارات الوحدة (ملفات الترجمة متطابقة، اتجاه اللغات، منع التحويل لمواقع خارجية) |
| `npm run test:db` | يطبّق الترحيلات على Postgres 16 مؤقت ويشغّل `supabase/tests/*.sql` (العزل والصلاحيات). يحتاج initdb وpsql |
| `npm run build && npm run test:e2e` | اختبارات متصفح على الجوال وسطح المكتب. تقرأ من Supabase الحقيقي ومحاولة دخول خاطئة فقط، ولا تنشئ بيانات |

## متغيرات البيئة

| المتغير | إلزامي | الوصف |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | نعم | عنوان مشروع Supabase |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | نعم | المفتاح العام (`sb_publishable_…`). آمن للمتصفح؛ الحماية عبر RLS |
| `NEXT_PUBLIC_SITE_URL` | نعم في الإنتاج | عنوان الموقع، تُبنى منه روابط تفعيل البريد |
| `NEXT_PUBLIC_PLATFORM_NAME` | لا | اسم المنصة الظاهر. فارغ = الوصف العام من ملفات الترجمة |

لا يستخدم التطبيق أي مفتاح سري (لا `service_role`). كل الكتابة الحساسة تمر بدوال قاعدة بيانات تتحقق من الصلاحية.

## النشر (Vercel)

1. Import المستودع واختيار المجلد الجذر `auto-parts`.
2. إضافة متغيرات البيئة أعلاه، و`NEXT_PUBLIC_SITE_URL` = النطاق الفعلي.
3. في Supabase ← Authentication ← URL Configuration: إضافة `https://<النطاق>/auth/confirm` إلى Redirect URLs.
4. إعداد SMTP خاص (Authentication ← SMTP). البريد الافتراضي في Supabase محدود جدًا ولا يصلح لمستخدمين حقيقيين.

## قاعدة البيانات

- الترحيلات في `supabase/migrations`. تُطبّق على مشروع جديد دفعة واحدة عبر `supabase/manual/setup_new_project.sql` (SQL Editor ← Run).
- كانت المنصة على مشروع مشترك، لذلك كل الجداول والأنواع تبدأ بـ `ap_`، والدوال المساعدة في مخطط `ap_private` غير المنشور عبر API.
- لا يوجد مشغّل على `auth.users`؛ الملف الشخصي يُنشأ عند أول دخول عبر `ap_ensure_profile`.

| الجدول | الغرض |
|---|---|
| `ap_locales` | اللغات المفعّلة واتجاه الكتابة |
| `ap_profiles` | ملف المستخدم (الاسم، الجوال، الحالة) |
| `ap_user_preferences` | اللغة المفضلة والمنطقة الزمنية |
| `ap_roles_permissions` | مصفوفة صلاحيات أدوار الإدارة |
| `ap_staff_roles` | أدوار فريق الإدارة لكل مستخدم |
| `ap_organizations` | المنشآت (pending / active / suspended) |
| `ap_organization_members` | أعضاء المنشأة (owner / admin / staff) |
| `ap_organization_verifications` | كل صفة (وسيط، بائع، مورد، مصنع، ناقل) تُعتمد أو تُرفض منفصلة، مع السبب ومتخذ القرار |
| `ap_audit_logs` | سجل تدقيق تلقائي بمشغّلات، للقراءة فقط |
| `ap_platform_settings` | إعدادات المنصة (مثل أقصى عمر لتأكيد التوفر: 48 ساعة) |

### تعيين أول مدير أعلى (مرة واحدة)

1. أنشئ حسابك من `/signup` وفعّل البريد وسجّل الدخول مرة.
2. في Supabase ← SQL Editor:

```sql
insert into public.ap_staff_roles (user_id, role)
select id, 'super_admin' from auth.users where email = 'بريدك@example.com';
```

بعدها تُدار بقية الأدوار من `/admin/access`.

## مسار الشريك (B1)

1. المدير ينشئ دعوة من `/admin/invitations` (بريد + صفات + لغة + مدة). الرمز عشوائي (32 بايت)، يُخزَّن بصمته فقط، ويُعرض الرابط مرة واحدة.
2. المدعو يفتح `/invite/<token>`، يسجّل أو يدخل **بنفس البريد المدعو**، ثم يقبل الدعوة: تُنشأ منشأة معلّقة وطلب اعتماد مسودة.
3. يعبّئ `/partner/application`: بيانات المنشأة والممثل والصفات والإقرار، ويرفع المستندات (PDF/JPG/PNG حتى 4MB، يُفحص النوع من محتوى الملف) إلى مساحة تخزين خاصة `ap-verification-docs`.
4. يرسل الطلب؛ لا يُقبل الإرسال قبل اكتمال الحقول الإلزامية ووجود مستند واحد على الأقل.
5. المدير يراجع من `/admin/partner-applications`: موافقة على صفات محددة، رفض، أو طلب تعديل (السبب إلزامي). الموافقة على طلب ناقص تحتاج سبب استثناء يُسجَّل.
6. فتح أي مستند يمر بـ `/api/documents/<id>`: يُسجَّل في سجل التدقيق ثم رابط مؤقت لدقيقة.

جدول الصفات المطلوبة لكل طلب (`partner_application_roles` في الوثيقة) هو `ap_organization_verifications`.

## الكتالوج (B2)

- **تعريف القطعة منفصل عن العروض:** `ap_products` (الاسم، العلامة، الفئة، الوصف بلغته الأصلية) و`ap_product_offers` (عرض لكل منشأة: نوع القطعة، السعر بعملته، بلد التوريد، مدة التوريد، الصلاحية).
- **أرقام القطع** في `ap_product_identifiers` تُحفظ كما كُتبت، ويُبحث فيها بصيغة موحّدة (بلا مسافات أو شرطات، أحرف كبيرة).
- **التوفر:** كل تأكيد يُحفظ في `ap_inventory_snapshots`. العرض «متوفر» للزائر فقط إن أُكّد خلال `availability_max_age_hours` (48 افتراضيًا). المخزون المجهول `null` لا صفر. تغيير السعر يُسقط التأكيد السابق.
- **النشر:** المنتج مسودة ← بانتظار المراجعة ← منشور/مرفوض (بسبب) ← موقوف. لا يضيف منتجًا أو عرضًا إلا شريك معتمد بصفة بائع أو مورد أو مصنع، ومنشأته نشطة.
- **العرض العام:** `ap_search_products` و`ap_public_offers` لا تكشفان هوية المنشأة (بلد التوريد فقط)، ولا تعرضان إلا المنشور والنشط وغير المنتهي من منشآت ما زالت معتمدة.
- الموديلات يضيفها المدير من `/admin/catalog`؛ العلامات الخمس والفئات العامة مُضافة مسبقًا.

## طلبات التسعير والطلبات (C)

1. العميل (بعد الدخول) يرسل `/request-part`: العلامة والموديل والسنة والمحرك، رقم الهيكل (اختياري، 17 خانة)، رقم القطعة، الوصف، الكمية، المدينة، الجوال، وحتى 3 صور في مستودع خاص `ap-request-media`. موافقة الخصوصية إلزامية، وحد 10 طلبات في الساعة. من صفحة المنتج زر «اطلب تأكيد السعر والتوفر» يفتح الطلب مربوطًا بالمنتج والعرض.
2. الإدارة (`quotes.manage`) من `/admin/quotes/<id>` ترسل الطلب لمنشآت معتمدة للبيع فقط، وتقرر مشاركة رقم الهيكل أو لا.
3. المورد يرى في `/partner/requests` الطلبات المرسلة له فقط عبر `ap_supplier_requests`: بلا اسم العميل وجواله، ورقم الهيكل فقط إن شوركه. فتح الصور يُسجَّل في التدقيق. عرض واحد لكل منشأة (يُحدَّث)، ولا يرى عروض المنافسين.
4. الإدارة تقارن العروض، وتنشئ مسودة تسعيرة (الإصدار التالي) ببنود: سعر القطعة، الشحن الدولي والمحلي، الجمارك، الضريبة، رسوم الخدمة، خصم، أخرى. لكل بند حالة «مؤكد/تقديري» ومصدر ومستفيد. المبالغ بالريال؛ الخصم وحده سالب.
5. الإصدار يتطلب صلاحية مستقبلية وشروط إلغاء والبائع المسؤول وبند قطعة. قاعدة البيانات تحسب الإجمالي وتعلّم وجود بنود تقديرية، ويصبح الإصدار السابق «مستبدلًا». العميل لا يرى المسودات.
6. العميل يوافق على أحدث إصدار صالح فقط: تُحفظ نسخة ثابتة (`snapshot`) ويُنشأ طلب `ORD-…` بحالة `awaiting_payment` وحالة دفع `unpaid` لا يغيّرها العميل. لا تحصيل أموال في هذه المرحلة.


الصلاحيات تُطبّق في قاعدة البيانات (RLS ودوال `security definer` تفحص الدور)، لا بإخفاء عناصر الواجهة. اختبارات `supabase/tests/foundation.sql` تتحقق منها.

| الصلاحية | مدير أعلى | مدير العمليات | المالية | الدعم |
|---|:-:|:-:|:-:|:-:|
| إدارة الأدوار `roles.manage` | ✓ | | | |
| إعدادات المنصة `settings.edit` | ✓ | | | |
| اعتماد المنشآت `accounts.approve` | ✓ | ✓ | | |
| طلبات التسعير `quotes.manage` | ✓ | ✓ | | |
| قراءة سجل التدقيق `audit.read` | ✓ | ✓ | ✓ | |
| قراءة ملفات العملاء `customers.read` | ✓ | ✓ | | |
| المالية والعمولات والاسترداد | ✓ | | ✓ | |
| معالجة الدعم `support.handle` | ✓ | | | ✓ |

- العميل يرى ويعدّل ملفه فقط (الاسم والجوال)، ولا يعدّل حالته.
- عضو المنشأة يرى منشأته وأعضاءها وصفاتها فقط، ولا يرى أي منشأة أخرى.
- المالك لا يفعّل منشأته ولا يعتمد صفته؛ اعتماد أي صفة يفعّل المنشأة، وممارسة الصفة تتطلب اعتمادها هي (`ap_private.org_can`).
- الرفض والإيقاف يتطلبان سببًا مكتوبًا يظهر للمتقدم.
- إيقاف حساب إداري يسحب صلاحياته فورًا. لا يمكن سحب آخر مدير أعلى.
- الجلسات المجهولة (anonymous sign-in مفعّل في المشروع المشترك) لا تحصل على ملف ولا صلاحيات.
