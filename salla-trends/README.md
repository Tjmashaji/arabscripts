# رادار الترند لتجار سلة

منصة تعمل كتطبيق في متجر تطبيقات سلة: تعرض للتاجر **المنتجات الأكثر مبيعًا والأسرع صعودًا** في منطقته وتصنيفه، محسوبة من مبيعات حقيقية لمتاجر سلة المشاركة، مجمعة ومجهولة المصدر. ومعها توثيق المتجر وشارة ثقة يتحقق منها العملاء.

> مشروع مستقل داخل المستودع `arabscripts`، ولا يمس المجلدات الأخرى.

## ما يعمل الآن وما يحتاج إعدادًا

| الوظيفة | الحالة |
|---|---|
| ربط سلة: استقبال الرموز بحدث `app.store.authorize` (Easy Mode)، وتشفيرها، وتجديدها قبل انتهائها بقفل يمنع التجديد المزدوج | يعمل ومختبر بشبكة مُحاكاة |
| الدخول عبر سلة (OAuth مع state ضد التزوير) | مكتوب؛ **يحتاج بيانات التطبيق** من بوابة الشركاء للتجربة الحقيقية |
| الويب هوك: التحقق من التوقيع على الجسم الخام، منع التكرار، إعادة المعالجة عند الفشل | يعمل ومختبر |
| الطلبات والمنتجات: الحفظ بلا بيانات عملاء، تحديث الحالة (إلغاء/استرجاع)، حذف كل شيء عند حذف التطبيق | يعمل ومختبر |
| سحب آخر 90 يومًا عند الربط (صفحة صفحة، مع احترام حد سلة وإعادة المحاولة) | يعمل ومختبر بشبكة مُحاكاة |
| مطابقة المنتج بين المتاجر (باركود GTIN أو اسم عربي موحد) والتصنيف الموحد وربط المدن بالمناطق | يعمل ومختبر |
| حساب الترند والأكثر مبيعًا (7 و30 يومًا × المنطقة × التصنيف) مع قواعد الخصوصية | يعمل ومختبر |
| لوحة التاجر، صفحة الترند بالفلاتر، فرص لمتجري، الإعدادات (الموافقة وحذف البيانات) | تعمل |
| التوثيق: طلب بسجل تجاري/عمل حر/معروف مع مستند، مراجعة المسؤول، صفحة تحقق عامة وشارة SVG | يعمل ومختبر |
| لوحة الإدارة: نظرة عامة، طلبات التوثيق، المتاجر | تعمل |
| الاشتراكات والدفع | **غير موجودة** (انظر «قبل الإطلاق») |

## كيف يُحسب الترند

- **المصدر الوحيد** هو مبيعات المتاجر التي ثبتت التطبيق ووافقت على المشاركة. لا نجمع بيانات من مواقع أخرى.
- **«شارك لترى»**: المشاركة متوقفة افتراضيًا. من لا يشارك لا تُحسب مبيعاته ولا يرى الترند (يُفرض في قاعدة البيانات عبر RLS، لا في الواجهة فقط).
- **مطابقة المنتج**: بالباركود إن كان صالحًا (مع رقم الفحص)، وإلا بكلمات الاسم بعد التوحيد: الهمزات والتاء المربوطة والتشكيل والأرقام العربية و«ال» والوحدات («١٠٠ مل» = «100ml»). اسم من كلمة واحدة لا يُطابَق.
- **الأكثر مبيعًا**: مجموع الوحدات. **الأسرع صعودًا**: `(الحالي − السابق) / √(السابق + 5)`، أي درجة z تقريبية تكافئ النمو القائم على حجم معتبر ولا تنخدع بقفزة من 1 إلى 4. الفترة السابقة بنفس طول الحالية.
- **الطلبات المحسوبة**: كل الحالات عدا الملغي والمسترجع وغير المدفوع.
- **الحساب** يتم مرة يوميًا (`/api/cron/trends`) في دالة SQL واحدة `app.compute_trends`، والواجهة تقرأ أحدث لقطة مكتملة.

### قواعد الخصوصية (في `db/migrations/0003_trends.sql`)

1. لا يظهر منتج إلا إذا باعه **3 متاجر مختلفة** على الأقل في نفس الفترة والمنطقة والتصنيف (`TRENDS_MIN_STORES`).
2. لا يظهر منتج يأتي أكثر من **70%** من مبيعاته من متجر واحد (`TRENDS_MAX_STORE_SHARE`).
3. نسبة النمو لا تُعرض إلا إذا حقق المنتج الشرط (1) في الفترة السابقة أيضًا؛ وإلا يظهر «ناشئ».
4. لا نخزن اسم العميل ولا جواله ولا بريده ولا عنوانه؛ فقط المدينة والدولة.

## ربط تطبيق سلة (بوابة الشركاء)

1. أنشئ تطبيقًا في [بوابة شركاء سلة](https://portal.salla.partners) واختر **Easy Mode** للمصادقة (الوضع المسموح للتطبيقات المنشورة في المتجر).
2. الصلاحيات: قراءة **الطلبات** و**المنتجات** وبيانات المتجر، و`offline_access`.
3. **Webhook URL**: `https://<APP_URL>/api/salla/webhook`، وانسخ **Webhook Secret** إلى `SALLA_WEBHOOK_SECRET`. نقبل استراتيجيتي Signature وToken.
4. اشترك في الأحداث: `app.store.authorize`، `app.installed`، `app.uninstalled`، `order.created`، `order.updated`، `order.status.updated`، `order.cancelled`، `order.refunded`، `order.deleted`، `product.created`، `product.updated`، `product.deleted`.
5. **Callback URL** للدخول: `https://<APP_URL>/api/auth/salla/callback`، وانسخ Client ID وClient Secret.
6. ضع رابط التثبيت من صفحة التطبيق في `SALLA_INSTALL_URL`.

> **تحقق قبل الإطلاق**: صيغة بعض حقول أحداث الطلب (مثل مكان مدينة الشحن وحالة `order.status.updated`) كُتبت من توثيق سلة مع قراءة متسامحة لعدة بدائل. جرّب على متجر تجريبي من البوابة وراجع `webhook_events` (الحمولة كاملة محفوظة 30 يومًا) قبل فتح التطبيق للعموم. وتأكد أن تطبيق Easy Mode يسمح بالدخول عبر OAuth بنفس الـ Client ID؛ إن لم يسمح فالبديل رابط دخول من لوحة سلة أو رابط سحري بالبريد.

## التشغيل محليًا

المتطلبات: Node.js 22.13+، وPostgreSQL 14+ (مختبر على 16).

```bash
cp .env.example .env.local          # ثم ضع TOKEN_ENCRYPTION_KEY: openssl rand -base64 32
npm install
PGPASSWORD=postgres ./db/setup-local.sh                 # الأدوار والقاعدة
MIGRATION_DATABASE_URL=postgres://trends_owner:trends_owner_dev@127.0.0.1:5432/salla_trends npm run db:migrate
```

معاينة بلا سلة (بيانات وهمية لـ 12 متجرًا وحساب الترند):

```bash
WORKER_DATABASE_URL=postgres://trends_worker:trends_worker_dev@127.0.0.1:5432/salla_trends npm run db:demo
echo DEV_LOGIN=true >> .env.local
npm run dev                          # ثم افتح http://localhost:3000/api/dev/login
```

حساب مسؤول:

```bash
MIGRATION_DATABASE_URL=... ADMIN_PASSWORD='كلمة-مرور-طويلة' npx tsx scripts/create-admin.ts admin@example.com "الاسم"
```

| الأمر | ماذا يفعل |
|---|---|
| `npm run typecheck` / `npm run lint` | الأنواع وESLint |
| `PGPASSWORD=postgres ./tests/global-db.sh && npm test` | يعيد إنشاء قاعدة الاختبار ثم يشغّل اختبارات الوحدات والتكامل (32 اختبارًا) |
| `npm run build` | بناء الإنتاج |

اختبارات التكامل على Postgres حقيقي تغطي: رفض التوقيع الخاطئ، تشفير الرموز، منع تكرار الحدث، حذف البيانات عند إلغاء التثبيت، العزل بين المتاجر، منع التاجر من توثيق نفسه، قواعد الخصوصية الثلاث، سحب الموافقة، الفرص، دورة التوثيق، التجديد المتوازي للرموز (تجديد واحد فقط)، المزامنة صفحة صفحة، وإيقاف المهمة عند رفض سلة للصلاحية.

## النشر

- **Vercel** (أو أي استضافة Node): `vercel.json` يشغّل المزامنة كل 10 دقائق والترند يوميًا. Vercel Cron يرسل `CRON_SECRET` تلقائيًا. خطة Hobby تسمح بالمهام اليومية فقط؛ المزامنة كل 10 دقائق تحتاج Pro أو مُجدولًا خارجيًا يستدعي `/api/cron/sync` بترويسة `Authorization: Bearer <CRON_SECRET>`.
- **قاعدة البيانات**: كل الجداول والدوال في مخطط `trends` مستقل، فتعمل المنصة داخل مشروع Supabase موجود دون أن تمس جداوله.
  - **Supabase**: `npm run db:supabase-sql > setup.sql` يولّد ملفًا واحدًا بكلمات مرور عشوائية (مطبوعة في رأسه). الصقه في **SQL Editor** وشغّله **مرة واحدة**. ثم استخدم **Transaction pooler** (منفذ 6543) من زر **Connect**، واسم المستخدم بصيغة `trends_app.<رقم-المشروع>` و`trends_worker.<رقم-المشروع>`.
  - **Postgres آخر**: نفّذ `db/roles.sql` بصلاحية superuser مع كلمات مرور قوية، ثم `npm run db:migrate` بدور `trends_owner`.
  - التطبيق يحتاج اتصالين: `DATABASE_URL` (trends_app) و`WORKER_DATABASE_URL` (trends_worker).
- **الصحة**: `/api/health`.

## الأمان

- **رموز سلة** مشفرة بـ AES-256-GCM، في جدول لا يملك دور الويب (`trends_app`) أي صلاحية عليه.
- **RLS** على كل الجداول: هوية المتجر تُضبط داخل كل معاملة (`app.store_id`)، فلا يرى متجر بيانات غيره حتى لو أخطأ الكود. تحديث التاجر لجدول المتاجر مقصور على أعمدة الموافقة.
- **الويب هوك**: HMAC-SHA256 على الجسم الخام بمقارنة ثابتة الزمن، وحد للحجم.
- **OAuth**: `state` عشوائي في كوكي httpOnly قصير العمر.
- **الجلسات**: رمز عشوائي في كوكي httpOnly/SameSite=Lax، وقاعدة البيانات تحفظ بصمته فقط. حذف التطبيق يُسقط جلسات المتجر.
- **وثائق التوثيق**: النوع من البايتات (PDF/PNG/JPG فقط)، 4 ميجابايت، وتُقدَّم للمسؤول فقط مع `CSP: sandbox`.
- **الشارة** تقرأ الحالة الحالية من القاعدة، فسحب التوثيق يظهر في كل مكان خلال 5 دقائق، ونسخها لمتجر آخر لا يفيد لأن الرابط يشير لصفحة المتجر الأصلي.
- حدود محاولات للدخول وطلبات التوثيق.

## قبل الإطلاق التجاري

1. تجربة كاملة على متجر تجريبي من بوابة سلة (انظر «تحقق قبل الإطلاق» أعلاه).
2. **مشكلة البداية الباردة**: الترند يحتاج 3 متاجر مشاركة على الأقل لكل منتج. خطط لإطلاق مع مجموعة تجار أوائل، أو اخفض `TRENDS_MIN_STORES` إلى 2 مؤقتًا (لا أنصح بأقل).
3. الاشتراكات والدفع: سلة توفر خطط اشتراك للتطبيقات من البوابة نفسها (الأحداث `app.subscription.*`)، ولم تُربط بعد.
4. سياسة الخصوصية والشروط بصياغة قانونية (الصفحة الحالية `/privacy` شرح مبسط)، ومراجعة متطلبات نظام حماية البيانات الشخصية.
5. تنبيهات للتاجر (بريد أو واتساب) حين يصعد منتج في تصنيفه.
6. تحسين المطابقة: المنتجات التي تُكتب بأسماء مختلفة جدًا ولا باركود لها لن تُدمج؛ يمكن لاحقًا إضافة مطابقة دلالية.
